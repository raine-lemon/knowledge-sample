# 평가 등급 분포 검증기 설계

## 1. 문제 정의 (Background / Problem)

「인사평가 운영지침」(HR-REG-001) 제6조 제2항은 평가 등급 분포를 S 10% / A 20% / B 50% /
C 15% / D 5%로 강제한다. 이 분포는 조직 간 평가 관대화를 억제하기 위한 장치이지만, 실제로
분포가 지켜지는지 확인하는 시점은 반기 결과가 전사 집계된 **이후**, 즉 인사담당이
「2026 상반기 인사평가 결과 리포트」 같은 사후 리포트를 만들 때뿐이다. 2026-01-15 개정으로
제11조(평가 보정회의)가 의무화되면서 1차 평가 종료 후 보정회의를 반드시 열게 됐지만
(제11조 제1항), 보정회의 참석자(2차 평가자 전원, 제11조 제2항)에게 사전에 주어지는 자료는
없다 — 보정회의 시작 시점에 "어느 조직을 먼저 봐야 하는지" 판단할 근거가 없다는 뜻이다.

2026년 상반기(2026H1) 차수의 실측 결과가 이 공백을 드러낸다. 전사 집계 기준 D등급 실제
비율은 3.1%(6명/196명)로 규정치 5%에서 -1.9%p, S등급은 8.7%(17명/196명)로 규정치 10%에서
-1.3%p 벗어났다 — 양 끝 등급 회피(중앙집중) 경향이며, 이 패턴은 2024H1 차수부터 매 차수
반복돼왔다. 문제는 이 전사 집계만으로는 편차가 **전 조직에 고르게 퍼진 현상인지, 소수
조직에 쏠린 결과인지 구분할 수 없다**는 점이다. 현재 리포트는 본부별 재직 인원(§1)만
공개하고 본부별 등급 분포는 집계하지 않는다. 즉 예컨대 특정 본부에서 D 부여 인원이 0명이라서
전사 D 비율이 낮아진 것인지, 모든 본부가 고르게 조금씩 낮은 것인지는 현재 어떤 문서에서도
확인할 수 없다. 보정회의(제11조)가 "조직 간 편차 조정"을 목적으로 한다고 명시돼 있음에도,
그 편차를 조직 단위로 계량화하는 도구가 없는 상태로 회의가 열리고 있는 셈이다.

평가 등급 분포 검증기는 이 공백을 메운다. 1차 평가가 마감된 직후, 보정회의 개최 전에 본부별
1차 평가 결과를 제6조의 규정 분포와 비교해 편차(%p)를 계산하고, 사전 정의된 threshold를
넘는 조직에 경고 플래그를 붙여 인사담당에게 리스트로 제공한다. 목적은 등급을 자동으로
바꾸는 것이 아니라, 보정회의가 논의를 시작할 지점을 좁혀 주는 것이다.

## 2. 목표 / 비목표 (Goals / Non-Goals)

**Goals**

- 본부(조직) 단위 1차 평가 등급 분포를 제6조 제2항 규정 분포와 비교해 등급별 편차(%p)를
  계산한다.
- 10명 미만 조직에 대해 제6조 제3항(상위 조직 합산 규정)을 자동 적용한다.
- 편차가 threshold를 초과하는 조직을 CLI 출력에서 상단에 노출해 보정회의 준비 시간을
  줄인다.
- 계산 근거(조직명, 인원, 등급별 실제/규정 비율, 편차)를 사람이 읽을 수 있는 표와 기계가
  읽을 수 있는 JSON 두 형태로 출력한다.
- dry-run을 기본값으로 한다 — 이 도구는 HRIS의 등급 데이터를 **읽기만** 하며 어떤 값도
  쓰지 않는다.

**Non-Goals**

- 등급 자체를 자동으로 조정하거나 추천하지 않는다. 등급 변경은 제11조에 따라 보정회의의
  사람 판단으로만 이루어진다.
- 개인별 등급 근거(성과평가 70점 + 역량평가 30점, 제5조)를 검증하지 않는다 — 이 도구는
  조직 단위 분포만 다룬다.
- 수습평가(제10조)는 대상이 아니다. 제10조 제2항이 명시하듯 수습평가는 애초에 제6조 분포를
  적용하지 않는다.
- 이의신청(제12조) 이후 등급이 변경된 경우의 소급 재계산은 이번 범위에 포함하지 않는다
  (§7 열린 질문 참고).
- 급여 인상률·상여 배율(제7조, 「급여규정」 제8·9조) 계산은 다루지 않는다. 등급 분포 검증과
  처우 반영은 별개 시스템 책임이다.

## 3. 설계 (Design)

### 3.1 아키텍처 개요

검증기는 상태를 갖지 않는(stateless) 단발성 CLI다. HRIS API에서 두 종류의 데이터를 읽어
메모리에서 계산하고 표준출력으로 결과를 낸다.

```
[HRIS API]
  ├─ GET /orgs/tree                         (조직 계층)
  └─ GET /evaluations/{year}/{half}/orgs     (조직별 1차 평가 등급 카운트)
        │
        ▼
[grade_validator.py]
  1. fetch: 두 엔드포인트 호출, 로컬 캐시 없음 (매 실행 최신 조회)
  2. merge: 제6조③ 소규모 조직 상위 합산
  3. evaluate: 조직별 등급 분포 편차 계산, threshold 판정
  4. render: 표 형식 stdout + --json 옵션 시 JSON 파일
        │
        ▼
[인사담당 — 보정회의 자료로 사용]
```

인사담당이 실행하는 사람이므로 별도 서버나 스케줄러는 두지 않는다. 향후 보정회의 캘린더
일정과 연동해 자동 실행하는 안은 롤아웃 2단계 이후로 미룬다(§6).

### 3.2 편차 계산 로직

핵심 계산은 조직별 등급 실제 비율에서 규정 비율(QUOTA)을 뺀 %p 값이다. 아래는 실제 구현의
핵심부다 (원문 `narintech/hr-tools` repo, `grade_validator/core.py`).

```python
from dataclasses import dataclass, field

QUOTA = {"S": 0.10, "A": 0.20, "B": 0.50, "C": 0.15, "D": 0.05}
DEFAULT_WARN_THRESHOLD_PP = 3.0  # 편차 경고 임계값(%p) — §7 열린 질문 참고


@dataclass
class OrgGrades:
    name: str
    headcount: int
    counts: dict[str, int] = field(default_factory=dict)

    def merge(self, other: "OrgGrades") -> "OrgGrades":
        merged_counts = dict(self.counts)
        for g, c in other.counts.items():
            merged_counts[g] = merged_counts.get(g, 0) + c
        return OrgGrades(self.name, self.headcount + other.headcount, merged_counts)


def apply_small_org_rule(orgs: dict[str, OrgGrades],
                          parent_of: dict[str, str]) -> dict[str, OrgGrades]:
    """제6조 제3항: 조직 단위 인원 10명 미만은 상위 조직에 합산해 산정한다."""
    result = dict(orgs)
    for name, org in list(orgs.items()):
        if org.headcount >= 10:
            continue
        parent = parent_of.get(name)
        if parent is None or parent not in result:
            raise ValueError(f"{name}: 10명 미만이지만 상위 조직을 찾을 수 없음")
        result[parent] = result[parent].merge(result.pop(name))
    return result


def grade_deviation_pp(org: OrgGrades) -> dict[str, float]:
    """등급별 (실제비율 - 규정비율) %p."""
    return {
        g: round(org.counts.get(g, 0) / org.headcount * 100 - QUOTA[g] * 100, 1)
        for g in QUOTA
    }


def evaluate(orgs: dict[str, OrgGrades], parent_of: dict[str, str],
             threshold: float = DEFAULT_WARN_THRESHOLD_PP) -> list[dict]:
    effective = apply_small_org_rule(orgs, parent_of)
    rows = []
    for org in effective.values():
        dev = grade_deviation_pp(org)
        max_abs = max(abs(v) for v in dev.values())
        rows.append({"org": org.name, "n": org.headcount, "deviation_pp": dev,
                      "max_abs_pp": max_abs, "warn": max_abs >= threshold})
    return sorted(rows, key=lambda r: -r["max_abs_pp"])
```

`apply_small_org_rule`은 10명 미만 조직을 발견하면 즉시 상위 조직에 합산한 뒤 그 결과로만
평가한다 — 즉 최종 출력에는 10명 미만 조직이 단독으로 나타나지 않는다. 예를 들어 데이터본부
산하 소규모 팀(7명)이 있다면 데이터본부 전체 카운트에 흡수된 뒤 "데이터본부" 한 줄로만
보고된다. 최상위 조직(본부)이 10명 미만인 경우는 현재 정의된 5개 본부 중 없으므로
(§4 데이터 소스 참고, 2026H1 최소 본부는 데이터본부 30명 재직) 아직 실제로 부딪힌 적은
없지만, `parent_of`에 매핑이 없으면 예외를 던져 조용히 누락되는 것을 막는다.

### 3.3 threshold와 경고

`max_abs_pp`(다섯 등급 중 절대 편차가 가장 큰 값)가 threshold 이상이면 `warn: true`를
붙인다. 초기값은 3.0%p로 잡았다 — 전사 집계 기준 최근 5개 차수(2024H1~2026H1)의 등급별
편차가 대체로 ±2%p 안쪽이었던 것에 견주어, 조직 단위에서는 표본이 작아 분산이 더 클
것이라는 가정 하에 다소 여유 있게 잡은 값이다. 통계적으로 검증된 값은 아니며 시범 운영
중 조정 대상이다(§7).

## 4. 데이터 소스

사내 HRIS(가칭)의 내부 API를 가정한다. 두 엔드포인트만 사용한다.

- `GET /api/v1/orgs/tree?asOf={date}` — 조직 계층(본부 → 팀). 본부 목록은 현재
  플랫폼개발본부·서비스개발본부·데이터본부·사업본부·경영지원본부 5개다. 응답에 각 조직의
  `parent_id`가 포함되어 `parent_of` 매핑을 만든다.
- `GET /api/v1/evaluations/{year}/{half}/orgs` — 1차 평가(보정 전) 등급 카운트를 조직별로
  집계해 반환한다. **1차 평가 원본**이어야 한다는 점이 중요하다 — 이미 보정을 거친 값으로
  이 도구를 돌리면 보정회의가 조정하려는 대상 자체가 사라진다. HRIS 쪽에서 1차 평가 마감과
  보정 확정 사이에 별도 상태 필드(`stage: "primary" | "calibrated"`)를 두고 있다는 전제이며,
  검증기는 항상 `stage=primary` 값만 조회한다.
- 인증은 사내 서비스 토큰(인사팀 내부용) 사용을 가정하며, 개인 식별 정보(사번, 성명)는
  조회 응답에 포함하지 않도록 HRIS 쪽에 집계 전용 응답을 요청한다 — 이 도구는 조직 단위
  카운트만 필요하고 개인 단위 데이터는 다루지 않는다.
- 휴직 등으로 "평가제외" 처리된 인원(제3조 제4항)과 수습 중 인원(제10조)은 HRIS 집계 시점에
  이미 분모에서 빠져 있다고 가정한다 — 이 전제가 맞는지는 API 계약 확정 시 재확인이
  필요하다(§7).

로컬 캐시나 별도 DB는 두지 않는다. 매 실행이 최신 조회다.

## 5. 출력 예시

아래는 가상 시나리오(실제 반기 데이터 아님 — 본부별 등급 분포는 현재 어떤 리포트에도
공개돼 있지 않아, 도구가 무엇을 드러내는지 보이기 위해 만든 예시다)에 대한 CLI 출력이다.
전사 합계는 2026H1 실제 리포트 값(S17/A43/B101/C29/D6, n=196)과 맞췄다.

```
$ hr-grade-check --half 2026-H1 --threshold 3.0

평가 등급 분포 검증 — 2026년 상반기 (1차 평가, 보정 전)
규정: 제6조 제2항 (S 10% / A 20% / B 50% / C 15% / D 5%), 소규모 조직 합산: 제6조 제3항

본부           인원   S편차    A편차    B편차    C편차    D편차   최대편차  경고
------------- ----  ------   ------   ------   ------   ------  --------  ----
경영지원본부    27   -6.3%p   +2.2%p  -13.0%p   +7.2%p   +9.8%p   13.0%p   [!]
데이터본부      28   +0.7%p   +1.4%p   +7.1%p   -4.3%p   -5.0%p    7.1%p   [!]
사업본부        39   -4.9%p   +3.1%p   +6.4%p   +0.4%p   -5.0%p    6.4%p   [!]
서비스개발본부   47   +0.6%p   +1.3%p   +3.2%p   -0.1%p   -5.0%p    5.0%p   [!]
플랫폼개발본부   55   +0.9%p   +1.8%p   +0.9%p   -2.3%p   -1.4%p    2.3%p

경고 4/5 본부 (threshold 3.0%p 초과)
D등급 0명 본부: 데이터본부, 사업본부, 서비스개발본부 (3개 본부)
※ 이 표는 보정회의 참고 자료이며, 등급 확정은 제11조 절차를 따른다.
```

`--json` 옵션을 주면 동일한 데이터를 `{"half": "2026-H1", "threshold": 3.0, "orgs": [...]}`
형태로 파일에 남겨, 인사담당이 보정회의 안건 문서에 붙여 넣거나 다음 차수와 비교할 수
있게 한다.

## 6. 롤아웃 계획

- **2026-H2 (2026년 하반기 차수, 실행 예정 4주 내, 제4조 제3항)**: 시범 적용 1차수. dry-run
  전용, 인사담당 1인이 수동 실행하고 결과를 보정회의 참고 자료로만 배포한다. 등급 확정
  절차(제11조)에는 영향을 주지 않는다.
- **2027-H1**: 시범 결과를 바탕으로 threshold 재산정, 조직 계층 API 안정성 확인 후 인사담당
  부서 표준 절차에 편입할지 결정한다. 편입 시 보정회의 소집 공지(제11조 제2항, 2차 평가자
  전원 참석 대상)에 검증기 출력을 자동 첨부하는 방안을 검토한다.
- 정식 채택 전까지는 이 도구의 출력이 등급 확정의 근거가 될 수 없다 — 제11조 제4항("보정회의를
  거치지 않은 평가 결과는 확정된 것으로 보지 아니한다")과 마찬가지로, 검증기 출력 역시
  보정회의를 대체하지 않는다는 점을 시범 운영 공지에 명시한다.

## 7. 열린 질문 (Open Questions)

- **소규모 조직 합산 후 편차 표기 단위**: 제6조 제3항에 따라 10명 미만 팀을 상위 본부에
  합산하면 원래 팀 라벨이 출력에서 사라진다. 팀장이 자기 팀 숫자를 보정회의 전에 확인하고
  싶어할 수 있는데, 합산 전/후 값을 둘 다 보여줄지, 아니면 규정대로 합산된 값만 노출할지
  정책 결정이 필요하다.
- **threshold 3.0%p의 근거**: 현재는 최근 5개 차수 전사 편차를 어림잡아 정한 값이다.
  본부 단위 표본(27~55명)에서는 등급 1명 차이가 이미 2~4%p를 좌우하므로, 표본 크기별로
  다른 threshold를 두어야 하는지(예: 표준오차 기반 동적 threshold) 검토가 필요하다.
- **1차 평가 데이터의 정확성 보장**: HRIS의 `stage=primary` 값이 실제로 보정 전 원본인지
  API 계약 단계에서 검증돼야 한다. 만약 일부 조직이 보정을 이미 반영한 값을 올리는
  운영 관행이 있다면 검증기의 전제가 깨진다.
- **평가제외자(제3조 제4항) 처리 위치**: 분모에서 이미 빠져 있다는 가정을 HRIS 응답
  스키마에서 명시적으로 확인할 방법이 없다 — 필드 계약 확정 필요.
- **이의신청 이후 재계산**: 제12조에 따른 이의신청으로 등급이 사후 변경되면(2026H1
  기준 인용 4건) 검증기가 이미 배포한 보정회의 자료와 최종 확정 등급 사이에 차이가
  생긴다. 이 차이를 별도로 추적할지, 애초에 검증기 범위 밖으로 둘지 결정이 필요하다.
