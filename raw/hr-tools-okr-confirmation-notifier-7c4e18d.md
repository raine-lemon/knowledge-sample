# OKR 확정 알리미 설계

## 1. 문제 정의

「인사평가 운영지침」 제5조 제3항은 성과평가 70점을 "대상기간 개시 시점에 확정된
OKR 달성도"로 산정하도록 규정한다. 즉 상반기는 1월 1일, 하반기는 7월 1일 이전에
각 조직이 OKR을 확정해두어야 그 반기의 성과평가가 규정대로 산정된다. 문제는 이
기한이 매 차수 반복적으로 지켜지지 않는다는 점이다.

`OKR_ONTIME` 지표(기한 내 확정 조직 수 / 전체 조직 수)를 5개 차수 연속으로 보면
추세는 다음과 같다.

| 차수 | 기한 내 확정 | 전체 | 준수율 |
|---|---|---|---|
| 2024-H1 | 9 | 16 | 56.2% |
| 2024-H2 | 10 | 16 | 62.5% |
| 2025-H1 | 11 | 17 | 64.7% |
| 2025-H2 | 12 | 18 | 66.7% |
| 2026-H1 | 14 | 19 | 73.7% |

준수율 자체는 5개 차수에 걸쳐 완만히 개선되고 있지만(56.2% → 73.7%, +17.4%p),
그 개선은 전적으로 인사담당의 수동 리마인드(메일·메신저 개별 발송)에 의존한
결과다. 조직 수가 16개에서 19개로 늘어난 만큼 수동 추적의 부담도 함께
늘었고, 담당자 1인이 반기 개시 2~3주 전부터 각 본부 담당자에게 개별 확인을
돌리는 방식은 확장성이 없다. 2026 상반기 리포트(§4 OKR 연동 현황)에서도
"기한 내 OKR을 확정한 조직은 전체 19개 중 14개(73.7%)였다"고 명시하며, 남은
5개 조직의 미준수가 여전히 구조적 문제로 남아 있다고 지적한다. 2026-07-30
인사위원회 회의록도 같은 수치를 재확인하며 "OKR 기한 미준수 5개 조직에 대해
본부장 면담을 실시한다"는 결정을 내렸다 — 이는 사후 조치이지 예방 조치가
아니다.

미준수의 하류 효과도 가볍지 않다. 제5조 제4항에 따라 대상기간 개시 후 목표가
변경되면 변경 전 목표를 기준으로 채점하고 변경 시점·사유를 기록해야 하는데,
이 예외 처리 자체가 "애초에 기한 내 확정이 안 됐다"는 방증인 경우가 실무적으로
섞여 들어온다. 즉 미확정과 기중 변경은 서로 다른 조항(제3항 vs 제4항)이 적용되는
별개 사안이지만, 현장에서는 둘이 뒤엉켜 평가 근거 정리를 어렵게 만든다.

OKR 확정 알리미는 이 반복 작업을 자동화해 기한 내 확정률을 끌어올리고, 인사담당의
수동 추적 공수를 없애는 것을 목표로 한다.

## 2. 목표 / 비목표

**목표**
- 반기 대상기간 개시일(1/1, 7/1) 이전에 OKR을 확정하지 않은 조직에 자동으로
  Slack 리마인드를 발송한다.
- 기한 초과 시 해당 조직 리더뿐 아니라 상위 라인(본부장)까지 에스컬레이션해
  인사위원회의 "본부장 면담" 결정이 상시적으로 선제 작동하도록 만든다.
- 기한 내 확정률을 다음 차수(2026-H2)부터 단계적으로 끌어올려, 최소 80% 이상을
  1차 목표로 삼는다.

**비목표**
- OKR 내용의 품질(목표 설정의 적절성, SMART 여부 등)은 검토하지 않는다. 이 봇은
  "확정 여부"라는 상태 플래그만 본다.
- 제5조 제4항이 규정하는 기중 목표 변경의 승인·기록 절차를 대신하지 않는다.
  기중 변경은 여전히 담당자가 OKR 관리 시스템에 수동으로 사유를 기록해야 한다.
- 강제 분포·등급 산정 로직에는 관여하지 않는다.

## 3. 설계

### 3.1 대상기간 개시 시점 계산

제5조 제2항에 따라 상반기 대상기간은 1/1, 하반기는 7/1에 개시된다. 리마인드는
개시일 기준 D-14부터 시작해 D-7, D-3, D-1까지 점증적으로 발송하고, 개시일 당일
(D-0)에도 미확정 조직이 남아 있으면 그 시점부터는 리마인드가 아니라 에스컬레이션
단계로 전환한다.

```python
# okr_notifier/schedule.py
from datetime import date, timedelta

REMIND_OFFSETS = (14, 7, 3, 1)  # 개시일 기준 D-14 ... D-1

def period_start(today: date) -> date:
    """해당 반기의 대상기간 개시일(1/1 또는 7/1)을 반환한다."""
    year = today.year
    h1_start, h2_start = date(year, 1, 1), date(year, 7, 1)
    if today <= h1_start:
        return h1_start
    if today <= h2_start:
        return h2_start
    return date(year + 1, 1, 1)

def next_run_kind(today: date) -> str | None:
    """오늘이 리마인드/에스컬레이션 발송일이면 종류를 반환, 아니면 None."""
    start = period_start(today)
    days_left = (start - today).days
    if days_left in REMIND_OFFSETS:
        return "remind"
    if 0 <= (today - start).days <= 6:  # 개시 후 1주 동안 매일 에스컬레이션
        return "escalate"
    return None
```

cron은 매일 09:00 KST에 1회 실행되며(`0 9 * * * python -m okr_notifier.run`),
`next_run_kind`가 `None`을 반환하는 날은 API 조회 없이 즉시 종료해 불필요한
호출을 피한다.

### 3.2 Slack 알림 로직

```python
# okr_notifier/notify.py
import requests

SLACK_WEBHOOK = "https://hooks.slack.com/services/…"  # 조직별 채널 라우팅은 config로 분리

def unconfirmed_orgs(okr_api) -> list[dict]:
    """OKR 관리 시스템에서 이번 반기 미확정 조직 목록을 가져온다."""
    orgs = okr_api.list_orgs(half=okr_api.current_half())
    return [o for o in orgs if o["status"] != "confirmed"]

def send_remind(org: dict, days_left: int):
    text = (
        f":alarm_clock: *[OKR 확정 알리미]* {org['name']} — "
        f"대상기간 개시까지 D-{days_left}\n"
        f"아직 OKR이 확정되지 않았습니다. 「인사평가 운영지침」 제5조 제3항에 따라 "
        f"개시 시점(D-0) 이후 확정 시 변경 전 목표 기준(제4항)이 적용될 수 있습니다.\n"
        f"<{org['okr_link']}|OKR 확정하러 가기>"
    )
    requests.post(org.get("slack_webhook", SLACK_WEBHOOK), json={"text": text}, timeout=5)

def send_escalation(org: dict, days_over: int):
    text = (
        f":rotating_light: *[OKR 확정 알리미 — 에스컬레이션]* {org['name']} — "
        f"대상기간 개시 D+{days_over}, 아직 미확정\n"
        f"본부장님 확인이 필요합니다. 인사위원회는 기한 미준수 조직에 대해 "
        f"본부장 면담을 결정 사항으로 두고 있습니다.\n"
        f"<{org['okr_link']}|지금 확정하기>"
    )
    requests.post(org["lead_slack_webhook"], json={"text": text}, timeout=5)
```

### 3.3 실행 흐름

1. cron이 매일 09:00 KST에 `run.py`를 실행한다.
2. `next_run_kind(today)`로 오늘이 리마인드일인지 에스컬레이션일인지 판정한다.
   해당 없으면 즉시 종료.
3. OKR 관리 시스템 API에서 `status != confirmed`인 조직 목록을 가져온다.
4. `remind` 단계면 조직 담당 채널로, `escalate` 단계면 본부장 채널(및 조직
   채널에 스레드로)로 메시지를 발송한다.
5. 발송 로그(조직, 단계, 발송 시각)를 내부 DB에 적재해 다음 차수 리포트의
   "알림 발송 이력" 근거로 남긴다.

## 4. 데이터 소스

OKR 확정 상태는 사내 OKR 관리 시스템(가칭 `okr-service`)의 REST API를
가정한다.

- `GET /orgs?half=2026-H2` — 조직 목록, 각 조직의 `status`
  (`draft` | `pending_review` | `confirmed`), `confirmed_at`, `okr_link`.
- `GET /orgs/{id}/leads` — 조직 리더·상위 본부장의 Slack 사용자 ID/웹훅 라우팅
  정보. 조직 구조(리더 → 본부장 체인)는 인사 시스템의 조직도 API와 동기화된
  스냅샷을 사용하며, 알리미 자체는 조직도를 직접 관리하지 않는다.
- 알리미는 이 API를 읽기 전용으로만 호출한다. 상태 변경(확정 처리)은 각 조직
  담당자가 OKR 관리 시스템에서 직접 수행하며, 알리미는 그 상태를 폴링할 뿐이다.

## 6. 에스컬레이션 정책

- D-14 ~ D-1: 조직 담당 채널에 리마인드만 발송. 톤은 안내 수준.
- D-0 (개시일 당일): 아직 미확정이면 그 순간부터 상태를 "지연"으로 표시하고
  본부장 채널에도 참조로 발송하기 시작한다.
- D+1 ~ D+6: 매일 본부장에게 에스컬레이션 발송. 이 구간이 2026-07-30 인사위원회
  결정 사항 4번("OKR 기한 미준수 5개 조직에 대해 본부장 면담을 실시한다")의
  실행을 앞당기는 지점이다 — 면담이 반기 말에 사후적으로 이뤄지던 것을, 개시
  직후 1주 내 선제 알림으로 당긴다.
- D+7 이후에도 미확정이면 자동 알림은 중단하고, 인사담당에게 수동 개입 필요
  목록을 별도 요약(주 1회)으로 보낸다. 봇이 무한정 재촉하는 것을 방지하고
  사람의 판단으로 넘기기 위함이다.

## 7. 롤아웃 계획

- **1단계 (2026-H2 적용, 9월 중 배포)**: 리마인드 단계만 우선 가동. 에스컬레이션은
  로그만 남기고 실제 발송은 보류해 오탐(조직 구조 매핑 오류 등)을 관찰한다.
- **2단계 (2026-H2 개시일 전후)**: 에스컬레이션 발송 활성화. 첫 사이클은
  인사담당이 그림자 모니터링하며 본부장 채널 라우팅이 정확한지 확인한다.
- **3단계 (2027-H1부터)**: 발송 로그를 반기 리포트의 §4 OKR 연동 현황에
  자동 첨부해, "알림 발송 → 확정 시점" 상관관계를 다음 차수부터 추적한다.

## 8. 열린 질문

- 제5조 제4항의 기중 목표 변경 건을 알리미가 어떻게 다뤄야 하는가? 현재
  설계는 `status: confirmed`만 보고 이후 변경 여부는 추적하지 않는다. 기중
  변경이 발생하면 별도로 조직에 "변경 전 목표 기준 적용" 안내를 보내는 것이
  나을지, 아니면 OKR 관리 시스템 쪽에서 변경 이벤트를 훅으로 알리미에 넘기게
  할지 결정이 필요하다.
- 조직 수가 16개 → 19개로 늘어난 것처럼 반기마다 조직 구조가 바뀔 수 있는데,
  이 변경을 알리미가 자동으로 반영할지, 매 반기 초 인사담당이 조직 목록을
  수동 확정할지 정해야 한다.
- 에스컬레이션 D+7 이후의 "인사담당 수동 개입" 단계를 다음 반기부터는 봇이
  인사위원회 안건 초안(미준수 조직 목록)까지 자동 생성하도록 확장할지는
  아직 논의되지 않았다.
- 본부장 면담 결과(면담 후 확정까지 걸린 일수 등)를 알리미 로그와 연결해
  효과를 정량 측정할 방법이 필요하다 — 현재는 별개 트랙(인사위원회 회의록)에만
  기록된다.
