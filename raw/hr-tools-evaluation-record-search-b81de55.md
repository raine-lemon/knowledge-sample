# 평가 근거기록 검색기 설계

- 상태: Draft (리뷰 대기)
- 작성: 인사(HR) 도구 개발팀
- 관련 문서: 「인사평가 운영지침」(HR-REG-001) 제12조·제13조, 2026 상반기 인사평가 결과
  리포트 §5, 평가자 교육자료(2026) — 평가 근거 기록 슬라이드

## 1. 문제 정의

2026년 개정 지침 제12조 제1항에 따라 인사담당 부서는 평가 결과를 통보할 때 등급
산정의 근거를 함께 제공해야 한다. 같은 개정에서 이의신청 심의 기한도 14일로
정해졌다(제12조 제3항). 그런데 등급 산정 근거 — 평가자가 각 등급마다 최소 2건씩
기록하는 관찰 행동 사례 — 는 현재 본부별로 서로 다른 스프레드시트(구글 시트 또는
로컬 엑셀 파일)에 흩어져 있고, 파일명 규칙도 본부마다 제각각이다. 인사담당자가
이의신청 1건을 심의하려면 다음과 같은 수작업을 거쳐야 한다.

1. 피평가자의 소속 본부를 확인한다.
2. 해당 본부 담당자에게 해당 차수 평가 스프레드시트 공유를 요청한다.
3. 시트 내에서 피평가자 행을 찾고, 근거 기록 셀(자유 텍스트)을 읽는다.
4. 과거 차수 기록이나 보정회의 변경 사유가 필요하면 이 과정을 차수별로 반복한다.

2026년 상반기 차수 기준 이의신청 접수는 10건, 이 중 인용(근거 부족·오류 인정)은
4건이었다(2026 상반기 인사평가 결과 리포트 §5). 인용률 40%는 근거 기록 자체가
부실했거나, 부실하지 않았어도 심의 담당자가 14일 안에 충분히 찾아 검토하지
못했을 가능성을 함께 시사한다. 실제로 지난 차수 심의 로그를 표본 확인한 결과,
근거 자료 확보에만 심의 기한의 30~40%가 소요된 사례가 다수 확인됐다. 승진
심사나 보정회의 준비 때도 동일한 병목이 반복된다 — 보정회의는 1차 평가 결과와
등급별 근거 기록을 지참해야 하는데(평가자 교육자료 §보정회의 참석 준비), 자료
취합이 회의 하루 전에야 끝나는 경우가 잦다.

이 설계 문서는 5년간 보존되는(제13조 제1항) 평가 근거 기록을 하나의 색인으로
모아, 평가자·인사담당이 피평가자·차수·등급·본부·키워드로 즉시 검색할 수 있는
내부 도구 "평가 근거기록 검색기"를 만드는 것을 목표로 한다.

## 2. 목표 / 비목표

### 목표

- 이의신청 심의, 재심의(제15조), 보정회의 준비, 승진 심사 시 과거 평가 근거
  기록을 차수·피평가자·등급·키워드로 검색해 30초 이내에 찾을 수 있게 한다.
- 5년 보존 의무(제13조 제1항)를 만족하는 저장소 하나로 본부별 스프레드시트를
  대체한다.
- 제13조 제2항이 규정한 열람 목적 제한 — "승진 심사, 이의신청 재심, 감사 목적
  외에는 열람할 수 없다" — 을 시스템적으로 강제한다. 이는 부가 기능이 아니라
  이 도구가 존재하기 위한 전제 조건이다. 접근 제어가 검증되지 않으면 검색
  성능이 아무리 좋아도 배포하지 않는다.
- 누가 언제 누구의 기록을 왜 조회했는지 감사 로그로 남긴다.

### 비목표

- 평가 등급 산정 로직이나 배점 계산(성과 70점/역량 30점) 자동화는 다루지
  않는다. 이 도구는 이미 확정된 근거 기록의 검색·조회만 다룬다.
- 평가자가 근거를 입력하는 화면(작성 UX) 개선은 범위 밖이다. 최초 버전은
  기존 스프레드시트 제출 결과를 배치로 색인하는 방식으로 시작하고, 작성
  단계 통합은 후속 과제로 분리한다(§8 열린 질문).
- 급여·상여 등 처우 정보 연동은 다루지 않는다. 「급여규정」(HR-REG-003)
  영역은 별도 시스템 소관이다.
- 실시간(초 단위) 색인 갱신은 목표하지 않는다. 차수 종료 후 배치 색인으로
  충분하다고 보고, 필요성이 확인되면 재검토한다.

## 3. 설계

### 3.1 개요

배치 파이프라인이 각 본부 스프레드시트 제출본을 정규화해 검색 색인에
적재하고, 조회 API가 요청자의 권한을 판정한 뒤에만 결과를 반환한다. 모든
조회는 감사 로그 테이블에 동기 기록된다 — 감사 로그 쓰기가 실패하면 조회
결과도 반환하지 않는다(fail-closed).

```
[본부 스프레드시트 제출본]
        │  (차수 종료 후 배치, 담당자 검수 완료본만)
        ▼
[정규화 파이프라인] ── 피평가자/평가자 사번 매핑, 등급 검증
        ▼
[검색 색인 (OpenSearch)]  ←─ 열람 로그와 별개로 원본은 append-only 저장소에도 적재
        │
        ▼
[조회 API] ── 권한 판정(§3.3) ── 감사 로그 기록 ── 결과 반환
        ▲
   [평가자 / 인사담당 웹 UI]
```

### 3.2 색인 구조 및 검색 쿼리 예시

근거 기록은 자유 텍스트이므로 풀텍스트 검색이 핵심이다. 정형 필드(피평가자
사번, 차수, 등급, 본부)로 먼저 걸러내고 본문은 형태소 분석기로 검색한다.
OpenSearch 인덱스 매핑과 조회 쿼리 예시는 다음과 같다.

```json
PUT /evaluation-records
{
  "mappings": {
    "properties": {
      "evaluatee_id":   { "type": "keyword" },
      "cycle":          { "type": "keyword" },
      "department":     { "type": "keyword" },
      "grade":          { "type": "keyword" },
      "rater_id":       { "type": "keyword" },
      "rater_role":     { "type": "keyword" },
      "evidence_text":  { "type": "text", "analyzer": "nori" },
      "recorded_at":    { "type": "date" },
      "retention_expires_at": { "type": "date" }
    }
  }
}
```

이의신청 심의 담당자가 특정 피평가자의 2026년 상반기 근거 기록을 검색하는
쿼리 예시:

```json
GET /evaluation-records/_search
{
  "query": {
    "bool": {
      "filter": [
        { "term":  { "evaluatee_id": "E-10432" } },
        { "term":  { "cycle": "2026H1" } }
      ],
      "must": [
        { "match": { "evidence_text": "지연 마감" } }
      ]
    }
  },
  "sort": [{ "recorded_at": "desc" }]
}
```

보정회의 준비 시에는 본부·차수 단위로 등급별 근거 건수를 집계해 "근거가
1건 이하인 등급"을 미리 찾아낸다 — 평가자 교육자료가 강조한 "근거가 약한
등급을 찾아내는 자리"를 회의 전에 선제적으로 지원하는 용도다.

```json
GET /evaluation-records/_search
{
  "size": 0,
  "query": { "bool": { "filter": [
    { "term": { "department": "서비스개발본부" } },
    { "term": { "cycle": "2026H2" } }
  ]}},
  "aggs": {
    "by_evaluatee": {
      "terms": { "field": "evaluatee_id", "size": 500 },
      "aggs": {
        "by_grade": {
          "terms": { "field": "grade" },
          "aggs": { "evidence_count": { "value_count": { "field": "evidence_text" } } }
        }
      }
    }
  }
}
```

### 3.3 접근 제어 로직

평가 기록은 민감정보다. 제13조 제2항은 열람 목적을 승진 심사·이의신청
재심·감사로 한정한다. 조회 API는 매 요청마다 다음 순서로 판정한다.

1. **요청자 역할 확인** — 인사담당(HR admin), 2차 평가자, 감사 담당자,
   인사위원회 재심의 위원 중 하나인가. 그 외 역할(예: 1차 평가자 본인,
   피평가자 본인)은 이 도구의 조회 대상이 아니다 — 본인 결과 통보는 기존
   통보 프로세스(제12조 제1항)를 그대로 쓴다.
2. **목적 코드 필수 입력** — 조회 시 `PROMOTION_REVIEW` /
   `APPEAL_RECONSIDERATION` / `AUDIT` 중 하나를 목적 코드로 선택해야
   조회가 성립한다. 목적 코드가 없는 요청은 API 레벨에서 거부한다(400).
3. **목적별 대상 범위 검증**
   - `APPEAL_RECONSIDERATION`: 현재 접수된 이의신청 케이스 ID와 피평가자
     사번이 일치해야 한다. 케이스가 종결(제12조 제3항 심의 완료 또는
     제15조 재심의 종료)되면 해당 케이스 기반 조회 권한도 함께 만료된다.
   - `PROMOTION_REVIEW`: 인사담당이 사전에 생성한 승진 심사 대상자
     명단(승진심사위원회 소집 시 확정)에 있는 사번만 조회 가능하다.
   - `AUDIT`: 감사 담당자 역할에 한해 기간·본부 단위 범위 조회를
     허용하되, 별도 감사 승인 티켓 번호를 함께 기록한다.
4. **본부 경계 완화 없음** — 2차 평가자라도 자신이 평가자로 관여하지 않은
   피평가자의 기록은 목적 코드 없이는 조회할 수 없다. "같은 본부니까"는
   접근 사유가 되지 않는다.
5. **거부 시 사유 로깅** — 권한 판정에서 거부된 시도도 감사 로그에
   `result: DENIED`로 남긴다. 반복 거부는 인사담당에게 주간 알림으로
   전달한다(오남용 조기 탐지).

## 4. 데이터 모델

핵심 엔티티는 `EvaluationRecord`(평가 근거 기록)와 `AccessLog`(열람 로그)
두 가지다.

**EvaluationRecord**

| 필드 | 타입 | 설명 |
|---|---|---|
| `record_id` | string (UUID) | 레코드 고유 ID |
| `evaluatee_id` | string | 피평가자 사번 |
| `cycle` | string | 평가차수, 예: `2026H1` |
| `department` | string | 평가 시점 소속 본부 |
| `grade` | enum(S/A/B/C/D) | 확정 등급 (보정회의 변경 반영 후 최종값) |
| `grade_before_calibration` | enum(S/A/B/C/D, nullable) | 보정회의 전 등급 |
| `calibration_reason` | text, nullable | 보정회의 변경 사유(제11조 제3항) |
| `evidence_items` | array<EvidenceItem> | 관찰 행동 사례, 등급당 최소 2건 |
| `rater_id` | string | 작성 평가자 사번 |
| `rater_role` | enum(PRIMARY/SECONDARY) | 1차/2차 평가자 |
| `source_file_ref` | string | 원본 제출 스프레드시트 참조(append-only 원본 위치) |
| `recorded_at` | datetime | 근거 기록 작성 시각 |
| `ingested_at` | datetime | 색인 적재 시각 |
| `retention_expires_at` | date | `recorded_at` + 5년(제13조 제1항) |

**EvidenceItem** (내장 객체)

| 필드 | 타입 | 설명 |
|---|---|---|
| `text` | text | 관찰 행동 사례 서술. "성실함" 같은 형용사형 서술은 검수 단계에서 반려 |
| `observed_at` | date | 관찰 시점(대상기간 내) |

**AccessLog**

| 필드 | 타입 | 설명 |
|---|---|---|
| `log_id` | string (UUID) | 로그 ID |
| `accessor_id` | string | 조회자 사번 |
| `accessor_role` | enum | 조회 시점 역할 |
| `purpose_code` | enum | PROMOTION_REVIEW / APPEAL_RECONSIDERATION / AUDIT |
| `reference_id` | string | 이의신청 케이스 ID / 승진심사 명단 ID / 감사 티켓 번호 |
| `queried_record_ids` | array<string> | 실제로 반환된 `record_id` 목록 |
| `query_summary` | text | 검색어·필터 조건 요약(원문 전체가 아닌 감사 가능한 요약) |
| `result` | enum(GRANTED/DENIED) | 판정 결과 |
| `requested_at` | datetime | 요청 시각 |

## 5. 감사 로그

제13조 제2항을 서류상 규정으로 남기지 않고 시스템으로 강제하려면, "누가
언제 누구의 기록을 왜 조회했는가"가 예외 없이 남아야 한다. 설계 원칙은
다음과 같다.

- **쓰기 우선(fail-closed)**: `AccessLog` 기록이 실패하면 조회 API는 결과를
  반환하지 않고 5xx를 반환한다. 로그 없는 열람은 존재할 수 없다.
- **거부 이력도 기록**: 권한이 없어 거부된 시도도 `result: DENIED`로 남긴다.
  이는 오남용 시도를 조기에 포착하는 신호가 된다(§3.3-5).
- **불변성**: `AccessLog`는 `EvaluationRecord`와 마찬가지로 append-only로
  운영한다. 수정·삭제 API를 제공하지 않는다.
- **정기 검토**: 인사담당 책임자가 분기 1회 `AccessLog`를 표본 검토해
  목적 코드와 실제 조회 대상의 정합성(예: `PROMOTION_REVIEW` 목적인데
  승진 심사 명단에 없는 사번을 조회했는가)을 점검한다. 이 검토 자체도
  `AUDIT` 목적 코드로 로깅된다.
- **보관 기간**: `AccessLog`는 대응하는 `EvaluationRecord`의
  `retention_expires_at`과 별개로, 감사 추적성을 위해 최소 5년 보관한다.
  원본 기록이 폐기된 뒤에도 "누가 조회했었는가"의 이력 자체는 남긴다(단,
  이 경우 `queried_record_ids`는 폐기된 레코드를 가리키는 참조로만
  남고 원문은 함께 삭제된다).

## 6. 5년 보존 후 처리 정책

제13조 제1항은 "평가 결과, 평가 근거 기록, 보정회의 변경 사유는 5년간
보존한다"고 규정할 뿐, 5년 경과 후 처리는 명시하지 않는다. 이 설계는 다음
기본 정책을 제안하며, 최종 확정은 인사위원회 승인을 받아야 한다(§8 열린
질문에도 재기재).

- `retention_expires_at`이 도래한 레코드는 검색 색인(OpenSearch)에서
  즉시 제외되어 더 이상 조회 결과에 노출되지 않는다.
- 원본 append-only 저장소의 레코드는 즉시 물리 삭제하지 않고, 만료 후
  90일간 "보류(soft-expired)" 상태로 유지한다. 이 기간 동안은 감사
  목적 코드로만, 그리고 인사담당 책임자 승인을 받은 예외 조회로만
  접근 가능하다 — 진행 중인 소송·감사가 있을 가능성을 대비한 유예다.
- 90일 보류 기간이 지나면 배치 작업이 물리 삭제를 실행하고, 삭제
  사실(레코드 ID, 삭제 시각, 승인자)만 별도 삭제 이력 테이블에 영구
  보존한다 — 본문은 남기지 않는다.
- 이의신청 재심의(제15조)나 감사가 진행 중인 레코드는 만료 시점이
  되어도 해당 절차가 종결될 때까지 자동 삭제 대상에서 제외(hold)한다.

## 7. 롤아웃 계획

1. **Phase 0 (설계 확정)**: 이 문서 리뷰, 접근 제어 목적 코드 체계에
   대한 인사담당·법무 검토, 5년 후 처리 정책 인사위원회 승인.
2. **Phase 1 (과거 데이터 적재, 읽기 전용)**: 2024H1~2026H1 5개 차수의
   본부별 스프레드시트를 정규화해 색인에 적재한다. 이 단계는 조회
   전용으로만 열고, 신규 작성 워크플로는 건드리지 않는다.
3. **Phase 2 (제한 사용자 파일럿)**: 인사담당 부서 내부에서만
   `APPEAL_RECONSIDERATION` 목적으로 시범 사용. 2026년 하반기 차수
   이의신청 심의에 실제 투입해 심의 소요 시간 변화를 측정한다.
4. **Phase 3 (2차 평가자 확대)**: 보정회의 준비 용도로 2차 평가자에게
   `PROMOTION_REVIEW`·본인 관여 건 조회 권한을 확대한다.
5. **Phase 4 (신규 근거 기록 직접 연동)**: 스프레드시트 배치 적재를
   대체해, 평가자가 근거를 입력하는 시점부터 이 시스템에 직접 기록하는
   구조로 전환한다(별도 설계 필요, §8).

각 단계 전환 전에 접근 제어 판정 로직에 대한 침투 테스트 성격의 점검
(권한 없는 역할로 조회 시도 → 전량 DENIED 확인)을 통과해야 다음 단계로
넘어간다.

## 8. 열린 질문

- 5년 보존 만료 후 처리(§6)의 90일 보류 기간과 최종 물리 삭제 주체는
  인사위원회 승인이 필요하다 — 아직 확정되지 않았다.
- 현재 근거 기록은 자유 텍스트라 "성실함" 같은 비구체적 서술을 완전히
  걸러내지 못한다. 작성 단계 검수 룰(예: 최소 글자 수, 날짜 포함 여부
  검증)을 이 도구가 강제해야 하는지, 아니면 평가자 교육으로만 다뤄야
  하는지 결정이 필요하다.
- 조직 개편(제14조)으로 소속 본부가 바뀐 피평가자의 과거 기록을
  현재 본부 기준으로 재매핑할지, 평가 시점 본부 기준으로 고정할지
  정책이 필요하다. 현재 데이터 모델은 평가 시점 본부(`department`)를
  고정값으로 저장하는 쪽으로 가정했다.
- 감사 담당자의 `AUDIT` 목적 조회는 범위가 넓어(본부·기간 단위) 오남용
  위험이 다른 목적 코드보다 크다. 감사 승인 티켓 발급 프로세스를 이
  도구 밖의 어떤 시스템과 연동할지 아직 정해지지 않았다.
- 검색 색인(OpenSearch)과 원본 append-only 저장소가 이중화되는데,
  둘 사이 정합성 검증(색인 누락·중복) 배치를 별도로 설계해야 하는지
  검토가 필요하다.
- 수습평가(제10조)는 등급 분포를 적용하지 않고 30-60-90일 목표
  기준으로 별도 운영되는데, 이 도구의 검색 대상에 수습평가 기록도
  포함할지는 아직 범위에 넣지 않았다.
